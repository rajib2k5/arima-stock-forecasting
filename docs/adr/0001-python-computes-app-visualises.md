# ADR-0001: Python computes, the app only visualises, and a versioned JSON contract sits between them

**Status:** Accepted (milestone 0)
**Date:** 2026-10-28
**Deciders:** the learner (owner of this repo), with the milestone-0 architect session

---

## Context

This repo is a public learning project. It re-does a course exercise (an ARIMA model of
Apple's daily closing price) carefully, and it has three kinds of reader:

1. **The learner**, who must be able to explain every number in an interview.
2. **A reader of the notebooks**, who wants the statistics step by step.
3. **A visitor to the web app**, who wants to *play* with the results: a price explorer, a
   stationarity lab, a 3D AIC landscape, an animated walk-forward forecast, residual plots.

Several forces pull on the design:

- **One number, one origin.** If the notebook says the test RMSE is $4.12 and the app says
  $4.15, the project has failed at its main job. A number must be computed in exactly one
  place.
- **The statistics live in Python.** `statsmodels` (state-space ARIMA with a Kalman filter)
  and `pmdarima` (`auto_arima`) have no equivalent in the browser that would give the same
  answer to the last digit.
- **Numbers must be re-measurable.** Every milestone ends with a verifier who re-runs the code
  and checks each number the write-up quotes. So the output must be reproducible and
  traceable to the exact code that made it.
- **Free, static hosting.** The app should run on GitHub Pages: no server to pay for, patch or
  keep awake.
- **Market data is not ours.** Prices come from Yahoo Finance through `yfinance`. Yahoo's terms
  restrict redistribution (this is a reading of their terms, not legal advice), and adjusted
  prices change after the fact (see "Why raw data stays outside the repo" below).
- **Two codebases drift.** Whenever one program writes data and another reads it, they slowly
  stop agreeing unless something checks them against each other.

## Decision

**All computation happens in the Python package `arima_forecasting`. Python writes its results
as JSON files with a fixed, versioned envelope. A static React 19 app reads those files and
draws them. The app never computes a statistic.**

In detail:

1. **Python is the only place numbers are made.** The package (`src/arima_forecasting/`) holds
   every calculation: download, cleaning, log transform, unit-root tests, the AIC grid, fits,
   forecasts, back-transforms, metrics. Notebooks *import* the package; they never copy its
   code. Notebooks are generated by `tools/build_notebooks.py`, and a test fails if a committed
   notebook no longer matches its builder.

2. **One JSON file per artifact.** `tools/export_app_data.py` writes
   `app/public/data/<artifact>.json` (for example `meta.json`, later `aic_grid.json`). Every
   file has the same outer shape, the *envelope*:

   ```json
   {
     "schema_version": "1.0.0",
     "artifact": "meta",
     "generated_at": "2026-10-28T12:00:00Z",
     "source_commit": "<40 or 64 hex>|<40 or 64 hex>-dirty|uncommitted",
     "data": { "...": "..." }
   }
   ```

   The full field-by-field contract is in [`docs/architecture/contract.md`](../architecture/contract.md).
   The envelope's top level is **closed** and the `data` payload is **open** (see "Why the
   envelope is closed and the payload open" below).

3. **The app only visualises.** The app fetches the JSON, checks it, and renders it. It may do
   *pure UI transforms* in `app/src/lib` (format a number, map a value to a pixel, slice rows
   by date, interpolate an animation frame). It may not produce any number that is presented
   as a *result*: no RMSE, no refitting, no `exp()` back-transform, no rolling mean. The test
   for this rule is simple: if a number could appear in a notebook, it must come from the
   JSON.

4. **Raw data stays outside the repo.** The downloaded price file lives in
   `$VOL_DATA_DIR/arima-stock-forecasting/raw/` (default `~/data/vol-projects`), never in git.
   Only *derived* artifacts are committed (see the open question at the end about `prices.json`).

### Why each envelope field exists

| Field | What it protects against |
|---|---|
| `schema_version` (semver) | The app reading a file whose *shape* changed. The app accepts any `1.x.y` and refuses any other major version, with an error that says so. A refusal is loud and immediate; a silent misreading draws a wrong chart that nobody notices. |
| `artifact` | Files being swapped or misnamed. The app checks that `aic_grid.json` really says `"artifact": "aic_grid"`. |
| `generated_at` | Not knowing how old a file is. It honours `SOURCE_DATE_EPOCH` (the reproducible-builds convention): set it, and two exports of the same code and data produce **byte-identical** files. That needs one more rule, below the table: the dirty check leaves out the exporter's own output. Both sides apply the same calendar rules to the timestamp (years 0001–9999, no leap second), so they share one definition of a real instant. |
| `source_commit` | Not knowing which code produced a number. A git object name, 40 hex characters (SHA-1) or 64 (SHA-256, for a repository created with `--object-format=sha256`), points at the exact commit. `-dirty` means the working tree had uncommitted changes, so the object name alone cannot reproduce the file; `uncommitted` means there was no commit at all (a brand-new repo, as at milestone 0). A reviewer can see at a glance whether a number came from committed code. |

**The dirty check leaves out `app/public/data/`.** `source_commit` names the *code* that
produced a file. If the check counted the exporter's own output, the first export would rewrite
`meta.json`, and a second export of the same code would then report `-dirty`. Leaving that one
folder out is what makes the byte-identical claim above true: with `SOURCE_DATE_EPOCH` set, two
exports of the same code and data are byte-identical. Every other uncommitted change, untracked
files included, still makes the commit `-dirty`. Known limit: a file marked with
`git update-index --assume-unchanged` or `--skip-worktree` is invisible to `git status`, so a
change to it is not reported.

### Why the envelope is closed and the payload open

The envelope's five top-level keys are the part every artifact shares, so both readers treat
that level as **closed**: Python's `validate_envelope` and the app's `parseEnvelope` reject an
unknown top-level key as firmly as a missing one, and adding an envelope field is a major bump.
The `data` payload is **open**: the app ignores keys it does not know inside `data`, so a minor
version can add a field without breaking an older app. Both readers also apply the same
artifact-name pattern, `^[a-z][a-z0-9_]*$`.

Two readers in two languages drift unless something ties them together. Here that is one
fixture, `app/src/test/fixtures/envelope_cases.json`: a list of valid and invalid envelopes that
the Python and the TypeScript test suites both run. A rule changed on one side only fails a test.

### Why `allow_nan=False`

Python's `json.dumps` writes `float('nan')` as the bare token `NaN` and infinity as
`Infinity` by default (measured: `json.dumps(float('nan'))` returns `'NaN'`). Neither is valid
JSON (RFC 8259 has no such tokens), and the browser's `JSON.parse` rejects the **whole file**
when it meets one. So a single failed ARIMA fit, if it leaked a NaN, would blank an entire app
view, far away from the cause.

With `allow_nan=False`, `json.dumps` raises
`ValueError: Out of range float values are not JSON compliant: nan` (measured) and the export
stops before anything is written. The rule that goes with it: **a missing value is an explicit
`null`**, and wherever a reader needs to know *why* it is missing, a sibling field says so
(for example a failed AIC cell has `"aic": null, "status": "failed", "error": "..."`).

The same reasoning covers large integers. `JSON.parse` turns every number into a double, which
holds integers exactly only up to ±(2^53 − 1); a larger one is silently rounded. So `dumps`
refuses any integer outside that range instead of writing a number the app would misread.

### Why raw data stays outside the repo

1. **Redistribution.** Yahoo's terms restrict redistributing their data. Keeping the raw file
   out of a public repo is the conservative reading. (Not legal advice.)
2. **Adjusted prices change after the fact.** With `auto_adjust=True` (the `yf.download`
   default, `yfinance/multi.py:56`), yfinance rescales Open/High/Low by the ratio of Yahoo's
   adjusted close to the raw close and replaces Close with the adjusted close
   (`yfinance/utils.py:506-523`). Yahoo back-adjusts that series for every new dividend, so a
   re-download after an ex-dividend date changes *every earlier* Close slightly. (That part is
   Yahoo's behaviour; it cannot be checked offline. It is why the download is treated as a
   dated snapshot.) Committing the raw file would produce whole-file diffs on every refresh.
3. **Snapshot, not stream.** The raw file is downloaded once and kept with a small manifest
   (SHA-256, row count, download time, yfinance version). The `prices` artifact records that
   SHA-256, so a reader can tell which snapshot produced the numbers.
4. **One data root for several projects.** All of the learner's "vol" projects share
   `$VOL_DATA_DIR`, each in its own folder, so no project overwrites another's data.

### How drift between Python and the app is caught

Drift has three forms. Each has its own check.

| Drift | Example | Check |
|---|---|---|
| **Shape drift**: Python changes a field, the app still expects the old one | `aic` renamed to `aic_value` | Python validates each envelope (`contract.validate_envelope`) before writing. The app's production parsers (`app/src/lib/contract.ts`) run over **every real committed JSON file** in `app/public/data/` (`app/src/lib/contract.realdata.test.ts`): each must pass `parseEnvelope`, name itself correctly and pass its artifact's payload parser, and the files present must equal `meta.data.artifacts`. Hand-built fixtures cover the edge cases separately. Rename a field in Python, re-export, and the app's tests fail. |
| **Staleness**: code changed but nobody re-exported | a bug fix in the grid search, old `aic_grid.json` still committed | An export check mode regenerates every artifact into a temporary folder and compares the `data` part with the committed files (the same idea as the notebook sync test; the shared diagram kit that generates `docs/architecture/*.mmd` has a similar check, but that kit is not public yet and is planned to be vendored into `tools/diagrams/`). It compares `schema_version`, `artifact` and `data`, **not** `generated_at` or `source_commit`, because those two legitimately differ between the export run and the check run. |
| **Version drift**: a breaking change without a major bump | a field changes from dollars to log-dollars but keeps its name | Code review against the versioning policy in `contract.md`. Unit names are part of field names (`close_usd`, `log_close`) so a unit change *is* a rename, and a rename is a major bump. |

A note on `source_commit` and committing JSON: a file cannot contain the hash of the commit
that contains it. The workflow is therefore: commit the code, export on the clean tree (so
`source_commit` is that code commit, without `-dirty`), then commit the regenerated JSON in a
second commit. `provenance.source_commit` counts untracked files as dirty, so this only works
from a genuinely clean tree, which is the point. The one exception is `app/public/data/`
itself, which the dirty check leaves out (see "The dirty check leaves out `app/public/data/`").

## Options considered

### Option A: Jupyter notebooks only

| Dimension | Assessment |
|---|---|
| Complexity | Low: one language, the course's own format |
| Reproducibility | Weak: cells can run out of order; outputs saved in the file can come from code that has since changed |
| Interactivity | Medium in a live kernel (plotly can draw a 3D surface); none on GitHub, whose notebook viewer strips JavaScript |
| Testability | Weak: numbers live in cell outputs, not in a structure a test can check |
| Hosting | Free, but readers must run Python to interact |

**Pros:** closest to the course; nothing new to learn; notebooks are still part of this design.
**Cons:** no public interactive experience; numbers are hard to test; hidden state.
**Would win if:** the only audience were people willing to run Python, and the interactive views
were dropped.

### Option B: Streamlit or Dash (a Python web app)

| Dimension | Assessment |
|---|---|
| Complexity | Low to medium: one language |
| Reproducibility | Medium: numbers are recomputed on each interaction, so they depend on the server's environment at that moment |
| Interactivity | Good |
| Testability | Medium: logic and UI tend to mix |
| Hosting | Needs a running Python server; free tiers sleep and cold-start |

**Pros:** one language; can call statsmodels live.
**Cons:** a server to host; "computed once, verified, frozen" becomes "computed on demand"; less
control over the 3D landscape and the animation.
**Would win if:** visitors needed inputs that cannot be precomputed, such as any ticker or any
date range. Here every interactive choice is a small finite set (d in {0, 1, 2}, p and q in
0..5, three forecast methods, two test segments), so precomputing all of it is cheap.

### Option C: FastAPI backend + React frontend

| Dimension | Assessment |
|---|---|
| Complexity | High: two services, an API, deployment, CORS, security |
| Reproducibility | Medium: same as B |
| Interactivity | Excellent |
| Testability | Good (OpenAPI can serve as the contract) |
| Hosting | A server to pay for and secure |

**Pros:** live computation with a typed API.
**Cons:** the most moving parts, for no gain when every view can be precomputed.
**Would win if:** the input space were too large to precompute, or the data had to stay private
or be refreshed daily.

### Option D1: compute in the browser with Pyodide (Python compiled to WebAssembly)

**Pros:** no server; the real Python libraries could, in principle, run client-side.
**Cons:** every visitor downloads a Python runtime plus numpy, scipy and statsmodels before
seeing a chart; pmdarima has compiled extensions that would also need a WebAssembly build;
fitting 144 ARIMA models in a browser tab is slow, especially on a phone. The numbers would
still need checking against the Python run, so the contract problem does not go away.
**Would win if:** a "fit your own model" feature were essential and had to work offline.

### Option D2: re-implement ARIMA in TypeScript

**Pros:** fast, no server, small download.
**Cons:** two implementations of Kalman-filter maximum likelihood (with diffuse initialisation,
parameter transforms, an optimiser) will not agree to the last digit, and every disagreement
is a bug hunt. This *creates* the drift the project is trying to prevent, and doubles what
must be tested.
**Would win if:** never, for this project. It would only make sense if the TypeScript version
were the product and Python the reference.

### Option E (chosen): Python pipeline → versioned JSON → static React app

| Dimension | Assessment |
|---|---|
| Complexity | Medium: two languages, joined by one well-defined file format |
| Reproducibility | Strong: pinned versions (`==` via uv), `SOURCE_DATE_EPOCH`, `source_commit`, snapshot SHA |
| Interactivity | Good within the precomputed grid |
| Testability | Strong on both sides; the JSON is the seam where tests meet |
| Hosting | Free static hosting |

## Trade-off analysis

The deciding trade-off is **live flexibility against verified, frozen numbers**. Options B, C
and D buy the ability to compute on demand. This project needs the opposite: numbers computed
once, by one implementation, re-measured by a verifier, and shown identically in notebooks,
reports and the app. Since every interactive choice is a small finite set, precomputing all of
them costs a few minutes of CPU at export time and removes the server entirely.

The price is friction: a new view that needs a new number needs a Python change, an export and
a contract update. That friction is deliberate. It is the moment where a reviewer can ask
"where does this number come from?"

## Consequences

**Easier:**
- Every number traces to one function, one commit and one data snapshot.
- The app can be developed and tested without Python installed (the JSON is committed).
- Hosting is free and nothing runs server-side.
- The verifier re-measures numbers by re-running one export command.

**Harder:**
- Two validators (Python `contract.py`, TypeScript `contract.ts`) must agree. Mitigated by one
  shared fixture of valid and invalid envelopes that both test suites run, and by testing the
  app's parser against the real exported files.
- Visitors cannot fit an order outside the precomputed grid (for example ARIMA(7,1,3)).
- Committed JSON makes the repo carry derived data, so the file sizes need watching (budgets in
  `contract.md`).
- Refreshing the data changes the numbers, because of Yahoo's retroactive adjustment. This is
  why the out-of-sample window is frozen (2024-01-01 to 2026-10-01, end exclusive) and the raw
  file is a snapshot with a manifest.

**To revisit:**
- If a future milestone needs user-chosen inputs that cannot be enumerated, revisit Option B.
- If artifacts grow past their size budgets, consider a columnar layout (see `contract.md`).

## Open question for the learner (a decision, not a default)

**Should `prices.json` be committed?** It is derived, but it is essentially the adjusted close
series, the same information as the raw file this ADR keeps out of git. The options:

1. **Commit it** (proposed default): the app works on GitHub Pages straight from the repo. Risk:
   it is a redistribution of Yahoo-derived prices.
2. **Build it in CI**: needs network access in CI, and Yahoo's retroactive adjustments make the
   build non-reproducible.
3. **Commit only aggregates**, for example weekly closes or the log series rounded to 4 decimals:
   a weaker price explorer, a smaller footprint.

This is a risk the repo owner carries, so it is the owner's call. Milestone 1 should not ship
`prices.json` until it is made.
